## 2. 核心纯逻辑设计（src/core/sequence）

### 2.1 feedback.js —— 反馈统计（最高优先级，单测锁死）

```js
/**
 * 反馈统计（需求文档 §2.5/§2.6 唯一权威定义）。
 * S: 秘密序列；G: 猜想序列；均要求同长 L、数字 1..9 互不重复。
 * 返回 { asc, desc, solved }：
 *   asc/desc = 把 G 的每个数字替换为它在 S 中的下标得到排列 R 后，
 *              R 中「右侧存在更大/更小数」的元素个数（末位永不计入）。
 *   solved   = asc === L-1 && desc === 0（R 严格递增 ⟺ G === S，充要）。
 */
export function statOf(seq) { … }            // 对任意序列统计 (asc, desc)
export function feedback(secret, guess) { … } // 核心；内部校验，非法输入 throw TypeError
export function validateGuess(guess, L) { … } // { ok, reason? }：长度/范围/重复校验
```

要点：
- `statOf` 独立导出——高阶变体、教学示例（需求 §2.3 例 1）都复用它；
- 复杂度 O(L²)，L ≤ 9，无性能问题；
- **安全性：本模块只在服务端参与含 secret 的计算；客户端 copy 仅用于本地回显计算展示与「重复猜想查重」缓存（输入 guess 仍能本地算出会收到的反馈——这是允许的，因为反馈本来就不含新信息）。**

> 设计说明（客户端能否本地算反馈）：可以。反馈是 guess 的确定函数，玩家本地预演不构成作弊；但**服务端仍然独立计算并下发**，客户端计算仅用于：① 提交前预览；② 断线恢复时本地校对。真相以服务端为准。

### 2.2 generator.js —— 密码生成

```js
export function randomSecret(L, rng = Math.random)          // 1..9 洗牌取前 L（Fisher-Yates）
export function fromPool(levelNo, rng)                      // 前 20 关从结构化密码池取
export function buildPool()                                 // 生成覆盖全结构的池：
//   全升序、全降序、山形（先升后降）、谷形、单峰双谷、纯随机
//   每结构 × 每长度(4/5/6) × 若干代表样本；求解器全量验证 12/8 次内可解后才入池
```

- 入门关（1~8）额外约束：池中密码的 (asc, desc) 不取极端值（避免开局就 (3,0) 导致玩家困惑）；教学第 1 关固定密码 `(2,7,3,9)`（与需求例 1 一致，教学闭环）；
- 双人版设密：服务端 `validateGuess` 通过后锁定，见 §4.3。

### 2.3 solver.js —— 可解性验证（仅开发/CI 用）

- 候选集 = P(9, L) 全排列枚举（L=4: 3024；L=6: 60480，内存可承受）；
- 策略：**贪心最大信息增益**——每轮在剩余候选集中选使反馈分区熵最大的猜想（首轮固定 `(1,2,3,4,…,L)` 预计算）；
- 用途：`npm run test` 中全量验证「池中每个密码 ≤ 次数上限可解」+ 随机抽样 2000 个随机密码验证平均轮次（需求 §5.1 数据来源）；
- **不打包进客户端/服务端产物**（esbuild 由入口可达性自动 tree 掉；tests 直接 import）。

### 2.4 levels.js —— 关卡与星级

## 3. 服务端设计

### 3.1 消息协议（新增 `seq.*` 命名空间，复用 `{ type, payload, requestId }` 信封与 error 回执约定）

#### 单人模式
**单人模式完全不走服务器**（无对抗、无作弊面），纯前端闭环：生成器 + feedback 在客户端跑。理由：单机无泄题问题（密码就在本地），省一次网络往返与服务器压力。→ **单人 = useSequence.js 本地状态机**。

> 备选方案（已否决）：单人也走服务端。否决理由：需求 NFR-01 的安全要求针对「答案不可被读取」，单机模式下答案本来就在玩家设备上，无保护对象；上服务器徒增复杂度。若未来加「每日挑战防作弊排行榜」，再补服务端生成（见 §6 演进）。

#### 双人模式（1v1）

| 方向 | type | payload | 说明 |
|---|---|---|---|
| C→S | `seq.room.create` | `{ name, token? }` | 建双人房（2 座位） |
| C→S | `seq.room.join` | `{ name, roomId, token? }` | 加入 |
| C→S | `seq.room.leave` | `{}` | 离开 |
| C→S | `seq.round.setSecret` | `{ secret: number[] }` | 设密方锁定密码（仅 SETTING 阶段、设密方） |
| C→S | `seq.guess` | `{ guess: number[] }` | 猜方提交 |
| C→S | `seq.round.again` | `{}` | 双方确认再来一局（镜像顶牛子 settleContinue） |
| S→C | `seq.room.state` | `{ room }` | 房间快照广播 |
| S→C | `seq.round.state` | `{ view, yourRole }` | 对局快照（按角色过滤，见下） |
| S→C | `seq.round.result` | `{ result, view }` | 终局 |

`seq.round.state.view`（按请求方过滤的私有视图）：

```js
{
  phase: 'SETTING' | 'GUESSING' | 'ROUND_OVER',
  L, triesMax, triesLeft,
  role: 'setter' | 'guesser',
  myGuesses: [ { seq: [..], asc, desc, solved } ],  // 自己视角的历史
  theirGuesses: [ { seq: [..], asc, desc } ],        // 对方视角历史（双人同屏显示同份数据）
  hintsUsed, hintOffers: [..] /* 可用提示内容，服务端生成后下发 */,
  result: null | { winner: 'setter'|'guesser', secretRevealed: bool },
}
```

**关键安全约束（NFR-01 / AC-09 / AC-12）**：
- `secret` 字段**永不出现在任何 S→C 消息**中，包括设密方自己的快照；
- 仅 `seq.round.result` 且 `phase === 'ROUND_OVER'` 且对局正常结束时，`result.secretRevealed=true` 时才回显密码（单人复盘 / 双人败方揭晓，产品可配置，默认揭晓）；
- 设密方提交后服务端立即校验+锁定，返回 ack 不含回显。

### 3.2 服务端状态机（sequenceRooms.js）

```
WAITING ──双方就位──> SETTING ──设密方锁定──> GUESSING ──猜中/次数尽──> ROUND_OVER ──双方 again──> SETTING
   ↑                    │                        │
   └──────掉线清理────────┴──────猜方断线宽限 60s──────┘
```

### 3.3 RoomManager 复用策略

顶牛子 `rooms.js` 的 RoomManager 与 4 座位、骨牌 AI、骰子编排深度耦合，**不继承不修改**，新写 `SequenceRoomManager`，但**复刻其成熟机制**（直接抄实现模式）：

| 机制 | 来源（顶牛子） | 阶梯密码处置 |
|---|---|---|
| token 会话 + tokens Map 索引 | rooms.js `makeToken/roomOf` | 照抄 |
| 断线宽限 60s + gone 标记 | `onDisconnect` | 照抄（双人局一方断线另一方看到「等待重连」） |
| 30s sweep 清理死房 | `sweep()` | 照抄（ROOM_IDLE_MS 同 5min） |
| 心跳 ping/pong | index.js | 复用同一 wss，天然继承 |
| 结算确认 + 超时 | `settleContinue/finishSettle` | 简化为 2 人版 |
| 防幽灵成员（findMemberByConn） | rooms.js | 照抄 |

单人房不需要——单人全在前端。

## 6. 安全与演进

### 6.1 首期安全模型
- 双人：secret 仅服务端；抓包断言（AC-12）进 CI；
- 设密方改口：提交即锁定，服务端 SETTING→GUESSING 单向迁移，无回退消息；
- 猜方暴力枚举：反馈函数确定性 ⇒ 猜方理论上可离线求交（这正是玩法本身），无需防护——**双人局信息对称（设密方拿到的反馈与猜方一致），无不对称作弊面**。

### 6.2 演进路线（不在本期）
| 特性 | 触发条件 | 方案 |
|---|---|---|
| 每日挑战 + 排行榜 | 需要防作弊排行 | 服务端生成密码 + `seq.daily.*` 协议，当日全服同密码 |
| 对局录像回放 | 双人纠纷 | 服务端记录 guess 序列即可（反馈可重算），存储极小 |
| 小程序发布 | 顶牛子二期 | uni-app 条件编译，sequence 页面天然跨端；ws 层已兼容 |
| 高阶变体上线 | M4 | variant.js 纯函数替换 feedback 调用点，UI 加模式徽章 |
